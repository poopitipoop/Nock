QUESTION 1: HOW EXACTLY IS PEARL'S WORK ATTEMPT BEING REUSED?

Short answer: Matrices A and B are committed once per (sigma, mu) block template.
The search loop only varies (t_rows, t_cols) offsets — selecting different
row/column strips from the already-committed and noised matrices.

Exact commitment chain (fiat_shamir.rs, prover.rs:BlockContext::build):

  attempt_state = block_state(block_commitment, nonce)
                = len(block_commitment) || block_commitment || len(nonce) || nonce

  kappa         = BLAKE3(attempt_state || params_tag)     // commitment_key()
  HASH_A        = BLAKE3(pad(A_row_major), key=kappa)     // matrix_commitment()
  HASH_B        = BLAKE3(pad(B_col_major), key=kappa)
  s_B           = BLAKE3(kappa || HASH_B)                 // noise_seed_b()
  s_A           = BLAKE3(s_B || HASH_A)                   // noise_seed_a()
  pow_key       = BLAKE3_derive("ai-pow v3 pow-key",
                    s_A || len(nonce) || nonce)

For Pearl-compatible merge mining (pearl_compat.rs):
  - sigma = Pearl incomplete block header (76 bytes) — contains Nockchain
            block commitment in the coinbase/aux
  - mu    = Pearl mining configuration (52 bytes)
  - Pearl jackpot key IS s_A directly (not pow_key_for_nonce)

Per-attempt ticket selection (pearl_compat.rs:compute_pearl_pattern_ticket,
pearl_mining.rs:run):

PatternOffsetSpace enumerates valid (t_rows, t_cols) pairs. For each pair:
  1. Select row indices from rows_pattern.shifted(t_rows)
  2. Select col indices from cols_pattern.shifted(t_cols)
  3. Run compute_pattern_tile_trace_from_slices -> TileState M (512-bit, 16xi32)
  4. Jackpot hash: BLAKE3(M, key=s_A)
  5. Check against Pearl-adjusted target AND Nockchain-adjusted target

Work factor / target adjustment:
  Both targets multiplied by: dot_product_length x h x w
  where dot_product_length = k - (k % rank), h = rows_pattern.size(),
  w = cols_pattern.size()

TileState mechanics (matmul.rs):
  fold(step, x): M[step % 16] = rotl13(M[step % 16]) XOR x_step
  Per stripe: accumulate t×t i32 block, XOR all into x, fold into M
  keyed_hash(pow_key): BLAKE3(M_as_64_bytes, key=pow_key)

Low-rank noise (matmul.rs:BlockNoise::expand):
  E = E_L * E_R, F = F_L * F_R
  Generated from s_A (for E) and s_B (for F)
  Entry range: i8, |A+E| <= 127, |B+F| <= 127

Critical security fix (audit doc 2026-05-31, prover.rs):
  Pre-fix: BlockContext::build took no nonce. Cached s_A and tile states;
  mine_inner applied pow_key_for_nonce(s_A, nonce) as final hash key.
  ONE expensive matmul could be reused for MANY cheap nonce trials — a PoW
  soundness bug.
  Fix: Nonce now included in attempt_state BEFORE kappa derivation.
  Every new nonce forces: fresh kappa -> HASH_A -> HASH_B -> s_A ->
  noise -> matrices -> tile states.
  BlockContext fields are now crate-private.

QUESTION 2: DOES NOCKCHAIN'S ZK PROOF WRAP PEARL'S OR REPLACE IT?

REPLACES. Completely independent proof system.

Pearl's proof system (not used by Nockchain):
  - Plonky2 three-layer recursive stack, ~60 KB compact proofs
  - Pearl submits PlainProof to Pearl Gateway via submitPlainProof
  - Never touches Hoon or Nockchain consensus

Nockchain's ZK proof system — 3-layer STARK
(ai-pow-zk/src/lib.rs, 2026-06-07_COMPACT_RECURSIVE_PRODUCTION_PIPELINE.md):

  Layer 0 — Useful-Work STARK
    System:    Plonky3 composite batch-STARK over Goldilocks + Tip5 MMCS
               with 7 LogUp buses (CompositeFullAirWithLookupsPinned)
    Soundness: 60 FRI query bits (log_blowup=4, 15 queries, pow=0)

  Layer 1 — Tip5 Recursive Proof
    System:    In-circuit Tip5 permutation verifier; computes Tip5 digest
               over Layer-0 public values; exposes digest as binding lanes
    Soundness: 60 FRI query bits (log_blowup=3, 20 queries)

  Layer 2 — Native BLAKE3 Final STARK
    System:    Native BLAKE3 outermost STARK; binds Layer-1 statement digest
               as 10 base-field public binding lanes

Compact production output:
  Full jammed %ai-pow artifact:          125,382 bytes
  Cold proof build wall time:             31.837s
  Accepted relaxed target:               ~150 KB, ~32s, 60-bit soundness

Layer-0 soundness binding:
  - Canonical program derived by VERIFIER from public parameters (not prover)
  - BLAKE3 strip-opening rows authenticate A/B strips to HASH_A/HASH_B
  - noised_packed LogUp bus binds matmul reads to committed plain bytes
    plus verifier-derived noise
  - A malicious miner cannot fabricate x_steps, swap strips, or skip matmul

Layer-0 public inputs (60 Goldilocks field elements):

QUESTION 3: DOES A MINER NEED PEARL SOFTWARE?

Partially. No Pearl software needed for computation. Pearl Gateway server IS

What ai-pow-miner provides natively:
  - All Pearl matmul logic (pearl_compat.rs)
  - PatternOffsetSpace: full (t_rows, t_cols) enumeration
  - Pearl wire format construction (AIP1, PMP1, NPA1)
  - PearlPlainProof serialization as base64(bincode-1.3.3)
  - Nockchain's own 3-layer ZK proof stack

What requires Pearl Gateway (JSON-RPC):
  getMiningInfo:
    Provides Pearl incomplete block header (sigma) and mining config (mu).
    Miner embeds "NOCKCHAIN-AI-POW-AUX" || aux_commitment in coinbase_aux_flags.
    Refresh interval: 1000ms; request timeout: 2000ms
  submitPlainProof:
    Submits Pearl-format PlainProof for Pearl target hits.

Miner loop summary (run.rs:run):
  1. Connect to Nockchain node via gRPC
  2. Poll Pearl Gateway getMiningInfo (1s interval)
  3. Receive Nockchain candidate block from node stream
  4. nock_block_commitment = BLAKE3(jam(candidate.block_header))
  5. Build PearlMergeMiningJob (binds nock_block_commitment in aux)
  6. Enumerate PatternOffsetSpace; for each (t_rows, t_cols):
       a. Evaluate ticket against both targets
       b. Pearl-only hit: submit PlainProof; keep Nockchain candidate
       c. Nockchain hit: build 3-layer recursive ZK cert; poke node;
                         clear candidate; request new candidate
       d. Both hit: submit to both; clear both
  7. Cache prover between runs

QUESTION 4: WHAT DOES "SETTLES NOCKCHAIN" MEAN TECHNICALLY?

Pearl matmul IS Nockchain's consensus PoW function. Not a side reward.

When a Nockchain block is valid:
  BLAKE3(TileState, key=s_A) <= nockchain_adjusted_target

Chain of cryptographic pre-commitment:
  1. Nockchain constructs candidate block
  2. nock_block_commitment = BLAKE3(jam(block_header))
  3. nock_block_commitment -> PearlNockchainAux -> NPA1 -> Pearl coinbase
     input script (txid-committed, not witness)
  4. sigma = Pearl incomplete header, which NOW contains the coinbase
             containing the Nockchain aux commitment
  5. kappa = BLAKE3(sigma || mu)  -- binds Nockchain candidate cryptographically
  6. All downstream values derive from this committed sigma

Security consequence: A miner CANNOT find a valid Pearl tile ticket and then
choose which Nockchain block to claim it for. The block was committed before
kappa was derived. Changing the Nockchain block candidate requires restarting
the entire Pearl work instance.
